# Misskey Play でミニゲームを作るときの指針（AI 向け）

人向けの説明は playground の「📖 ガイド」（`docs/guide/minigame.md`）にあります。ここでは、AI がゲームを設計・実装・検証するときの決まりごとをまとめます。
短い例は [examples/README.md](examples/README.md) の「ガイドの例」にあります。

## 前提（Play でできないこと）

- キーボードの入力、マウスの移動、ドラッグ、Canvas での描画はできない。入力はボタン・入力欄・switch・select と、MFM の `$[clickable]` のタップだけ
- 音は鳴らせない。画像は絵文字とカスタム絵文字（`:name:`）だけ
- 外部との通信は `Mk:api` だけで、本番の Play ではログインしていない扱いになる。ランキングのような共有データは作れない。代わりに `Ui:C:postFormButton` で結果を投稿してもらう

## ファイルの形（おすすめ）

ゲームの中身（ステージ、ルール、文章）を上に、部品とテストを下に置きます。人も AI も、直す場所をすぐ見つけられます。
サンプルの「ゲームのひな形」（[examples/template.ais](examples/template.ais)）がこの形です。書き換えて使ってください。

```
/// @ 1.2.1
// ===== 1. ゲームの中身（ここを書き換える）=====
let STAGES = [...]
// ===== 2. 状態とルール =====
var state = ...
@move(dx, dy) { ... }
// ===== 3. 画面と開始 =====
Ui:render([...])
reset()
// ===== ここから下は部品（触らなくてよい）=====
:: Lib { @grid(...) { ... } @pad(...) { ... } }
// ===== テスト（playground でだけ動く）=====
@tests() { Test:check("...", @() { Test:eq(...) }) }
if exists PLAYGROUND tests()
```

- 名前空間は実行の前に読み込まれるので、下の `:: Lib` を上から `Lib:grid()` のように呼べる。ただし `@関数` は読み込まれないので、トップレベルで使う関数は、使う場所より上に書く
- 名前空間に `var` は置けない。状態は 2. に置き、部品には引数で渡す。そうすると部品をテストしやすい
- テストの書き方は [testing.md](testing.md) を参照

## 構成の型

```
1. 定数（ステージ、絵文字の対応表）
2. 状態（var）
3. 表示用の部品を変数に作っておく（Ui:C:* の第2引数に id を付ける）
4. render(): 状態から部品を update する。状態を変えたら必ず呼ぶ
5. 操作の関数（move、undo、reset など）: 状態を変えて render() を呼ぶ
6. Ui:render([...]) で部品を並べる
7. 初期化（load(0) など）
```

- 状態を変える処理と、表示を作る処理を分ける。表示は `render()` の1か所でだけ作る
- 関数は `@名前() { }` で宣言する。コールバックから後で呼ぶ関数は、宣言がコードの後ろにあっても動く
- 盤面は 2 次元の配列で持つ。書き換えは `grid[y][x] = v` でできる
- 1 手戻す機能は、動く前の状態か差分を配列に積んでおき、`pop()` で戻す

## 盤面の描き方

- `Ui:C:mfm` に、絵文字を並べた行を `Str:lf` でつないだ文字列を渡す。`size` を 1.5〜2 にすると押しやすい
- 押せるマスは `$[clickable.ev={x}_{y} {絵文字}]` にし、`onClickEv: @(ev) { let [x, y] = ev.split("_").map(@(s) { s.to_num() }) ... }` で受け取る
- 盤面にはカスタム絵文字を使わない。MFM の中でカスタム絵文字は高さ 2em、普通の絵文字は 1.25em なので、そのマスだけ大きくなってずれる。キャラクターのアイコンにカスタム絵文字を使いたいなら、盤面用のアイコンを別に持つ
- 名前やアイコンを表示する部品（メニューの題など）は `Ui:C:mfm` にする。`Ui:C:text` やボタンでは `:カスタム絵文字:` が展開されない
- マスの絵文字は幅が揃うものを使う。正方形の絵文字（🟫⬜⬛🟨🟥🟦🟩 など）は並べたときに崩れにくい。全角スペースや半角の記号は絵文字と幅が合わない
- 盤面の外側は壁と同じ絵文字にすると見栄えがよい（たとえば倉庫番なら、自分の位置から塗りつぶして部屋の中を判定する）

## 操作の作り方

- 十字キーは、MFM の絵文字（⬆️⬅️⬇️➡️）を `$[clickable]` でタップさせて作る。`Ui:C:buttons` は幅に下限があり、スマホでは 3 つ並べると折り返す。作り方は [mfm-layout.md](mfm-layout.md) を参照
- 十字キーに A・B（🅰️🅱️）を足すと、メニュー・メッセージ送り・戦闘まで 6 つのボタンで操作できる。メニューは ▶ を十字キーで動かし、A で決定、B でもどる。ボタンの数が場面で変わらないので、押す位置を覚えやすい
- 押す部品より上にあるもの（盤面・メッセージの欄）の高さを、どの場面でも同じにする。場面が変わるたびに押す位置がずれると、スマホで押し間違える
- 盤面のマスのタップでも動けるようにすると、スマホで遊びやすい
- 連続で押される前提で、1 回の操作の処理は軽くする

## 物語・分岐のあるゲーム（ゲームブックなど）

- 場面をデータとして持つ。`{ text, choices: [{ label, to, cond, effect }], enter }` のようなオブジェクトにし、条件・行動・結果の文章は関数で書く。「文字列か関数のどちらでも受け取り、関数なら呼んだ結果を使う」小さな関数（`@val(x) { if Core:type(x) == "fn" x() else x }`）を 1 つ用意すると、文章を固定にするか状況で変えるかを場面ごとに選べる
- **条件付きの選択肢は、行き止まりを作りやすい**。条件をすべて満たさないと選択肢が 1 つも出ない場面ができる。各場面に、条件なしで必ず出る選択肢を 1 つ置く。完成したら、全場面を調べて「条件なしの選択肢があるか」を確かめるとよい
- **場面に入るたびに自動セーブすると、詰むことがある**。戻り道のない場所に、体力が減った状態でセーブされると、何度やり直しても負ける。やり直したときは全快にする、強い敵からは逃げられるようにする、などで防ぐ

## 画面が切り替わる RPG のようなゲーム

フィールド・町・戦闘を行き来するゲームを作ったときの知見です。画面の作り方の詳細は [mfm-layout.md](mfm-layout.md) にあります。

- **場面ごとに地図を持つ**: フィールド・町・塔などを、それぞれ文字の配列の地図にする。`{ rows, tiles: { "#": "🧱", ... }, encounter: true }` のように、地図ごとに絵文字の対応と性質を持たせると、地図の切り替えは「いまの地図の名前」を変えるだけで済む。町の人は地図の文字（小文字など）で置き、ぶつかったら話す
- **画面の大きさをそろえる**: 自分を中心に 9×7 マスを切り出して描けば、地図の大きさが違っても画面の大きさは同じ。戦闘の画面も 9×7 マスの背景（⬛ など）にし、敵は `$[scale]` で見た目だけ大きくする
- **メッセージはウィンドウで送る**: メッセージとメニューを同じ「ウィンドウ」（いつも同じ行数）に出し、長い文章はページに分けて A で送る。戦闘では「1 人の行動（こうげき！〜ダメージ）」を 1 ページにまとめると読みやすい。ページごとに、その時点の HP を覚えておけば、文章と表示の HP がずれない
- **一度だけの演出はページに付ける**: MFM のアニメーションは止まらないので、演出（斬撃・爆発など）は、そのページを見せているあいだだけ文字に入れる
- **ステータスは重ねて出す**: HP や「つよさ」は、`position` で地図の上に重ねたウィンドウに出すと、画面の高さを変えずに済む（[mfm-layout.md](mfm-layout.md) の「レイヤーウィンドウ」）
- **区切りで敵の強さを変える**: 川や山脈で地図を区切り、橋や峠を越えると敵が強くなるようにすると、進む順番が自然に決まる。区切りは縦横につながっていないと、斜めのすき間から抜けられる場所ができやすいので、幅優先探索で「橋を通らないと先へ行けない」ことを確かめる
- **セーブを読んだら、派生した状態も戻す**: 位置だけ保存して「いまいる町」などを保存していないと、町の中で再開したときに店や宿屋が壊れる。読み込んだあとで、位置から計算し直す

## 部品の制約（間違えやすい）

- 省略できるプロパティに `null` を渡すとエラーになる。`color: if x "red" else null` ではなく、使わないときはキーごと書かない
- `hidden` が効くのは `Ui:C:container` だけ。クリア表示などは container で包み、`update({ hidden: false })` で出す
- `fgColor` を付けた container の中にボタンを置かない。ボタンの文字色だけが変わり、テーマによっては読めなくなる（[tips.md](tips.md) を参照）
- `Ui:C:select` は `default` を `update` しても表示が変わらない。表示を変えるときは select を作り直し、親の container の `children` を差し替える
- 文字列の連結に `+` は使えない。テンプレート文字列を使う

## よく使う機能

| やりたいこと | 書き方 |
| --- | --- |
| 自己ベストの保存 | `Mk:save("best_{level}", moves)` / `Mk:load(...)`（ないときは `null`） |
| 結果の共有 | `Ui:C:postFormButton({ text: "結果を投稿", form: { text: "...{Str:lf}{THIS_URL}" } })` |
| 日替わりの問題 | `let rng = Math:gen_rng(\`{Date:year()}-{Date:month()}-{Date:day()}\`)`、`rng(min, max)` で整数 |
| 毎回違う乱数 | `Math:rnd(min, max)` |
| タイマー | `let stop = Async:interval(ミリ秒, @() { ... })`、止めるときは `stop()`。1 回だけなら `Async:timeout` |
| 演出 | MFM の `$[tada 🎉]`、`$[jelly ...]`、`$[x2 ...]`。`tada` と `x2`〜`x4` は文字を大きくして場所を取るので、盤面の中では `$[scale]` を使う（[mfm-layout.md](mfm-layout.md)） |

## 検証のしかた

静的チェック・テスト関数・シナリオテストの使い方は [testing.md](testing.md) にまとめています。以下は、それらを使わずに確かめる場合も含めた進め方です。


ゲームは、playground のブラウザ操作 API（[browser-api.md](browser-api.md)）で実際に遊んで確かめる。

1. `window.__playground.run(code)` で実行し、`logs` に `error` がないことを確かめる
2. 部品に id を付けておき、`act([{ type: "click", id: "padRow", index: 2 }, ...])` で操作して、`state.ui` の `props.text` を読む。MFM で作った十字キーなら `{ type: "clickEv", id: "pad", ev: "u" }` で押す
3. パズルなら、ステージが解けることを別の方法で確かめる。たとえば倉庫番なら、手元のスクリプト（Python の幅優先探索など）で各ステージの解を求め、その解をボタン操作に直して `act` に流し、すべてのステージでクリア表示が出ることを確かめる
4. クリア後の表示、1 手戻す、やり直す、ステージの切り替え、自己ベストの保存も操作して確かめる
5. 盤面の見た目はスクリーンショットで確かめる（絵文字の幅のずれは、テキストを読むだけでは分からない）
6. 長いゲーム（RPG など）は、最初から最後まで遊ぶボットを書く。ボットは人と同じ入力（十字キーと A・B）だけで操作し、地図の上の道は幅優先探索で求める。状態は、playground でだけ作る隠した部品に JSON で入れておくと読みやすい（`if exists PLAYGROUND { ... }` の中で作る）。乱数で結果が変わるので、何度か回す
7. 押す部品の位置が場面で変わらないか、演出が動いているかは、[mfm-layout.md](mfm-layout.md) の「確かめ方」を参照

## 公開

完成したら、ユーザーに Misskey の `https://サーバー名/play/new` でスクリプトとして貼り付けてもらう。1 行目の `/// @ 1.2.1` は消さないこと（消すと古い処理系で実行される）。
